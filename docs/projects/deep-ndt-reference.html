01

프로젝트의 중심 주장

여러 결과물을 나열하기보다 제품의 상태를 바꾼 전환을 중심으로 설명한다.

경쟁 환경과 실제 검사 업무를 관찰하고, 제품·운영·판매에 흩어진 접점을 연결해 DEEP-NDT를 현장에서 사용할 수 있는 하나의 제품 경험으로 구조화했다.
Transition 01

기술 → 검사 업무

판독 영역을 중심으로 뷰어를 재구성하고, 실제 검사자의 판단과 기록 흐름 안에서 기능이 작동하도록 개선했다.

Transition 02

공통 화면 → 역할별 제품

플랜트 운영자와 검사자의 목적을 구분하고, 역할·권한·진입 흐름과 관리 기능을 다시 설계했다.

Transition 03

판독 결과 → 판매 가능한 보고서

제품 밖 Excel에서 이어지던 보고 업무를 소프트웨어 안으로 연결했고, 이 기능은 별도 상품으로 확장됐다.

02

기술은 작동했지만 제품은 준비되지 않았다

합류 당시에는 기술 검증을 위한 최소 기능만 존재했다. 실제 조직과 현장에서 사용하려면 제품의 범위부터 다시 정의해야 했다.

Implemented

초기 MVP에 있던 것

  • 회원가입과 로그인
  • 검사 데이터 업로드
  • AI 판독 뷰어
  • 결과 리포트 내보내기

Missing

제품화를 위해 필요했던 것

  • 운영자와 검사자의 역할 및 접근 권한
  • 탈퇴를 포함한 계정 수명주기
  • 검사 프로젝트, 설비, 결과와 데이터 관리
  • 제품 내 보고서 작성과 편집
  • 일관된 UI 패턴과 QA 기준
  • 교육, 가이드와 자격 인증 경험

Evidence placeholder · 초기 제품 캡처 실제 화면에 번호를 붙여 기능 중심 구조, 역할 미구분, 좁은 판독 영역을 설명한다. 시각 완성도보다 PoC와 운영 제품의 구조적 차이를 보여준다.

03

실제 검사 업무를 비교하고 기록하다

추측보다 실제 작업을 기준으로 삼았다. 검사자 6명이 동일한 환경에서 DEEP-NDT와 경쟁 제품으로 판독부터 보고서 작성까지 수행했다.

Method

관찰

작업 전 과정을 촬영하고, 단계별 정지·반복·화면 이동과 오류가 발생하는 지점을 기록했다.

Quantitative

시간 비교

경쟁 제품 대비 판독 및 결과 보고서 작성 시간이 어디에서 줄거나 늘어나는지 확인했다.

Qualitative

인터뷰

불편과 비효율뿐 아니라 AI 자동 판독을 어떤 조건에서 신뢰하거나 다시 확인하는지 들었다.

피드백의 우선순위는 단순한 사용 불편보다 판독 정확성과 설비 상태 판단에 미치는 영향을 먼저 고려했다.

판단 기준 검토 질문
검사 정확성 결함을 놓치거나 잘못 판단하게 할 가능성이 있는가?
설비 상태 판단 설비 상태를 파악하는 데 치명적인 영향을 줄 수 있는가?
작업 효율 불필요한 이동이나 반복 작업을 만드는가?
사용 이해 기능이나 결과의 의미를 오해하게 하는가?
빈도와 구현 조건 여러 사용자에게 반복되는가? 필요한 기술과 리소스는 무엇인가?

편집 메모: 수백 건의 원본 피드백을 모두 노출하지 않는다. 익명 처리한 피드백 보드 일부와 ‘관찰 → 영향도 판단 → 제품팀 결정 → 구현 → QA’의 흐름을 대표 사례로 보여준다.

04

판독에 집중할 수 있는 뷰어

모든 기능을 항상 보여주기보다 검사자가 데이터를 보고 판단하는 핵심 영역과 작업의 연속성을 우선했다.

Problem 01

판독 영역을 잠식한 메뉴

상단 메뉴줄과 아이콘이 포함된 서브 메뉴가 세로 공간을 길게 차지해 가장 중요한 판독 섹션이 상대적으로 좁았다.

  • 상단 메뉴를 드롭다운 구조로 정리
  • 기능 중요도에 따른 정보 위계 조정
  • 메뉴 표시·숨김 토글 추가
  • 부가 정보를 작은 영역에서도 식별 가능하게 재배치

Problem 02

결과 편집을 위한 맥락 이탈

뷰어에서 자동 작성된 결과를 수정하려면 매니지먼트로 이동해야 했다. 판단과 기록이 같은 작업인데도 화면이 분리되어 있었다.

  • 뷰어 안에서 자동 생성 결과 확인
  • 같은 맥락에서 결과 편집
  • 수정한 내용을 보고서 데이터와 연결
  • 불필요한 화면 이동 제거

검사자가 판독의 맥락을 벗어나지 않고 판단과 기록을 완료할 수 있게 했다.

Before · 기능 노출 중심

초기 뷰어 캡처메뉴 구조와 좁은 판독 영역 표시

After · 판독 업무 중심

개선 뷰어 캡처확장된 판독 영역과 인라인 편집 표시

05

하나의 공통 흐름을 역할별 제품으로

같은 제품을 사용해도 운영자와 검사자가 원하는 정보와 완료해야 할 과업은 달랐다.

Plant operator

플랜트 운영자

  • 프로젝트와 설비 상태 파악
  • 검사 진행 상황 관리
  • 결과와 보고서 확인
  • 조직과 데이터 관리

Inspector

검사자

  • 할당된 검사 확인
  • 데이터 업로드와 판독
  • 판독 결과 기록과 수정
  • 작업에 필요한 기능으로 빠르게 이동

사용자 역할에 따라 첫 화면, 우선 정보, 접근 가능한 기능과 핵심 과업을 다르게 구성했다.

구조화한 것

  • 타깃 사용자와 역할
  • 역할별 핵심 과업
  • 접근 권한 정책
  • 로그인 이후 진입 흐름

추가한 관리 영역

  • 검사 프로젝트 관리
  • 설비 관리
  • 검사 결과 확인
  • 데이터 관리

Evidence placeholder · 역할과 권한 역할·권한 매트릭스, 운영자와 검사자의 분기 플로우, 변경된 매니지먼트 정보 구조를 순서대로 배치한다.

06

판독 결과를 판매 가능한 보고서로

제품에서 끝난 판독과 Excel에서 다시 시작되는 보고 업무를 하나의 데이터 흐름으로 연결했다.

Before

분리된 보고 업무

  1. DEEP-NDT에서 판독
  2. 결과 내보내기
  3. 별도로 Excel 실행
  4. 고객사별 템플릿에서 다시 작성
  5. 수정과 검토
  6. PDF 변환 후 전달

After

연결된 제품 흐름

  1. DEEP-NDT에서 판독
  2. 결과 데이터를 템플릿에 자동 연결
  3. 제품 안에서 보고서 확인과 수정
  4. PDF로 내보내기

관찰한 문제

  • 판독과 보고서 작성 프로그램의 단절
  • 별도 Excel 라이선스 필요
  • 비정상적인 프로그램 설치 사례
  • 고객사별 템플릿 제작과 관리의 반복
  • 이미 생성된 데이터를 다시 다뤄야 하는 비효율

제품에 남은 변화

  • Excel 없이 제품 안에서 보고서 작성
  • 판독 데이터와 결과 보고서 연결
  • 템플릿 대응 구조 마련
  • 반복적인 제작 및 관리 부담 감소
  • 보고서 기능의 별도 상품화

확인 필요: ‘별도 상품’이 독립 제품, 별도 요금제, 또는 다른 검사 소프트웨어와 함께 사용하는 도구 중 어느 형태인지 확정한 뒤 최종 문구를 선택한다.

07

반복 개선을 제품의 체계로 남기다

수백 건의 피드백을 개별 수정으로 끝내지 않고, 다음 기능과 QA에도 적용할 수 있는 공통 기준으로 정리했다.

01

관찰과 기록

테스트, 인터뷰와 제품 사용 중 발견한 피드백을 수집했다.

02

영향도 판단

판독 정확성, 설비 판단, 작업 효율과 발생 빈도를 검토했다.

03

공동 결정

개선안을 제안하고 사업·개발·AI팀과 범위와 우선순위를 정했다.

04

설계와 구현

화면과 흐름을 설계하고 반복되는 UI 패턴과 상태를 정리했다.

05

제품·디자인 QA

의도한 기능과 표현이 구현됐는지 확인하고 다음 개선으로 연결했다.

반복 개발에 필요한 핵심 UI 패턴과 상태를 정리해 일관된 구현과 QA의 기준으로 사용했다.

08

제품 밖까지 이어지는 도입 경험

산업용 소프트웨어의 도입은 구매로 끝나지 않는다. 배우고, 자격을 증명하고, 실제 현장에서 참고하는 과정까지 제품 경험으로 보았다.

Adoption

교육과 지속 사용

  • 사용자 매뉴얼 템플릿과 문서 작성
  • Notion 기반 온라인 사용자 가이드 제안 및 운영
  • 사용자 교육 문서
  • 교육 수료증과 자격인증서
  • 실물 자격증 제작 및 발송

Go-to-market

시장에 설명되는 제품

  • 공식 홈페이지 1·2차 리뉴얼
  • 회사·상품·제품소개서
  • 고객 및 조달 제안서
  • 전시회 커뮤니케이션
  • 광고, 홍보물과 브랜드 에셋 관리

제품 UI부터 교육, 홈페이지와 제안서까지 기술의 가치가 일관되게 설명될 수 있도록 주요 접점을 연결했다.

편집 메모: 본문에는 온라인 가이드, 공식 홈페이지, 제품소개서와 전시회 등 대표 접점 3–4개만 사용한다. 명함, 스티커, 개별 광고와 반복 문서는 작은 아카이브로 압축한다.

09

공개 가능한 결과

NDA로 매출과 계약 규모를 밝힐 수 없어도 제품의 상태와 업무 구조가 어떻게 달라졌는지는 구체적으로 설명할 수 있다.

  • PoC 기능 구조에서 역할 기반 제품 구조로 확장
  • 플랜트 운영자와 검사자의 흐름 및 권한 분리
  • 프로젝트·설비·결과·데이터 관리 기능 구축
  • 판독과 보고서 편집 사이의 화면 단절 제거
  • Excel 의존 보고서를 제품 내 작성 흐름으로 전환
  • 보고서 기능의 별도 상품화
  • 사용자 가이드와 교육·인증 경험 구축
  • 검사 용역에서 실제 제품 활용
  • 소프트웨어 단독 판매 단계 진입

계약 규모, 매출, 도입 기업과 사용자 수는 비밀유지 의무에 따라 공개하지 않는다. 제품의 판매 여부와 공개 가능한 기능·프로세스 변화만 기술한다.

10

필요 자료와 편집 원칙

수백 개의 개선을 전부 보여주지 않는다. 제품의 상태를 바꾼 세 가지 판단을 깊게 설명하고 나머지는 범위를 증명하는 자료로 사용한다.

06

화면과 자료에 포함된 고객·설비 데이터 비식별화

여러 화면을 디자인한 기록이 아니라, 복잡한 기술을 현장에서 이해하고 구매하고 사용할 수 있는 제품으로 만들어간 기록.

이 파일은 포트폴리오 상세 페이지의 콘텐츠 순서와 증거 자료를 검토하기 위한 참조 문서다. 실제 게시본에서는 미확인 표현과 placeholder를 제거한다.
